# 项目经历与面试演示

v0.3 已增加千问候选重排、原文摘录核验、132条排序对照和24条问答的两组配对评测，当前自动化测试为48项。最新收益、成本及评审局限见 [排序与答案质量报告](RANKING_AND_ANSWER_QUALITY.md)。v0.2结果保留在 [检索改进报告](RETRIEVAL_IMPROVEMENTS.md)。

## 如何定位项目

项目名可用“知行：基于 LangGraph 的知识问答与工单助手”。背景是运维资料分散、回答依据难核对、故障信息需要人工整理，以及模型动作需要审批。当前使用虚构的星舟资料完成业务闭环，不描述为已服务真实企业。

你的贡献应基于自己实际参与和能够解释的内容填写。下面是已实现内容的描述素材，不能代替你对代码的学习、调整和验证。

## 项目描述素材

> 基于 LangGraph、FastAPI、千问及 SQLite 构建文档问答与工单助手，实现资料上传、带原文引用的问答、多轮对话，以及人工审核后创建工单的流程。

- 设计意图识别、检索、回答、草稿、审批和写入的状态图，使用检查点与 `interrupt` / `Command` 实现跨重启审批和失败节点恢复。
- 实现同义词 BM25 与真实千问向量的 RRF 混合召回、千问候选重排、标题与页码引用、连续原文摘录核验、无依据拒答，并对模型 JSON 输出、向量数值和引用 ID 进行校验。
- 通过请求 ID、会话状态认领、工单操作唯一键处理重复提交；故障注入测试验证“写入后异常”恢复时不会重复创建工单。
- 开发文档、对话、审批、工单和运行记录网页，加入检索对比预览；使用 SSE 展示执行过程，保存模型调用用量与耗时，完成 48 项自动化测试及可复现评测脚本。

v0.2历史量化表达：在132条自编数据的18条改写验证正例上，混合检索Hit@3从原始BM25的61.1%提高到94.4%；当时原FAQ从100%下降到94.4%，报告保留回退案例。v0.3已恢复这3条FAQ回退，建议使用下方最新素材。简历空间有限时，可优先写48项测试、持久缓存与幂等故障验证，面试时再解释小样本评测。

不要写“准确率提升到 100%”“P95 稳定小于 5 秒”“支持高并发企业生产系统”或“自研 LangGraph 框架”。当前没有足够证据支持这些表述。

v0.3新增描述素材：

> 在混合召回后使用千问进行结构化候选重排，并设计来源摘录校验、持久重排缓存与故障降级。在原132条回归集的18条验证正例上，Hit@1从66.7%提升到94.4%；完成24条问答的配对评测，分别记录事实、引用与拒答，并提供人工复核工具。48项自动化测试通过。

面试时同时说明成本：本次24题请求的P95从5.797秒增至11.364秒。小样本、自编数据及同模型评审不能写成整体准确率或独立盲测成果。

## 面试中值得解释的问题

| 问题 | 可以结合代码说明的重点 |
| --- | --- |
| 为什么使用状态图？ | 问答与建单分支不同；审批要暂停；失败后需要复用已完成状态；图节点让流程和恢复边界清楚 |
| 为什么仅有 Checkpointer 不够？ | 保存图状态不等于外部写入只执行一次；工单落库后检查点前仍可能中断，所以需要独立幂等键 |
| 为什么使用混合检索？ | BM25 捕获具体词项，向量补充跨语言及口语召回；RRF 合并排名，不同数据上仍可能回退，因此保留单路基线和关键词模式 |
| 如何处理幻觉？ | 依据检索、限定模型提示、结构校验、来源 ID 校验、无依据拒答；语义忠实度并未被完全保证，动作还需人工审核 |
| 审批重启后如何继续？ | 同一会话 thread_id 保存 interrupt 状态；恢复时读取持久草稿并传入决定，避免重新生成 |
| 为什么模型调用次数不同？ | 先理解意图及检索词，再生成回答或草稿；混合模式另记录查询及首次文档向量调用，缓存命中会减少调用，无依据时可跳过回答生成 |
| SSE 和模型流式输出有什么区别？ | 本应用流式发送节点事件，最终回答整体显示；没有逐 token 推送 |
| 浏览器隔离是不是用户认证？ | 不是。签名 Cookie 保证标识不被随意篡改并检查归属，但没有账号、组织和 RBAC |
| 评测结果可靠吗？ | 可复现，包含开发/验证划分和单路对照，但问题仍由自己编写；正则检查是代理指标，同模型辅助评审存在偏差；已提供逐题HTML、人工评分模板及绑定答案版本的评分导入，需要独立人员实际复核 |

## 演示时的重点

先展示一个有可打开原文的回答，再在同一会话要求整理工单。展示未审批时工单不存在，人工修正事实和优先级后才保存。最后展示服务重启仍能恢复待审状态，以及测试中对写入后故障的重复保护。

建议重点阅读 `engine.py`、`store.py` 与 `tests/test_workflows.py`，并自己增加一份业务资料和一组问题。能解释恢复机制和检索失败案例，比背技术名词更有说服力。

## 后续改进的验收条件

1. 引入新的真实或许可使用的文档，独立编写至少 100 条问题，保留盲测集；将答案正确性、引用忠实度和拒答质量分开评估。
2. v0.3已完成候选重排及旧工单问题回归；继续在新业务资料与独立评测中确认收益，并测试更低成本的专用重排模型。
3. 对更长多轮会话做上下文压缩；对运行与检查点做保留策略；用重复实验和实际并发测试确认资源边界。
4. 若要作为多人系统部署，再增加账号身份、资料权限、任务队列与共享数据库，并验证越权与恢复协调。

以上属于后续工作，不计入本版本已完成成果。
